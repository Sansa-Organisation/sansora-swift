# Sansora SDK contract (v0.2.1)

Every Sansora SDK (iOS, Android, Flutter, React Native) implements this. The
TypeScript reference in `packages/core/src` is authoritative where this text is
short:

| Topic | Reference | Fixtures (`sdks/conformance/fixtures`) |
| --- | --- | --- |
| Paywall definition `sansora.paywall/1` (0.2.1: optional `legal.textGooglePlay`, a string of at most 300 characters like `text`; 0.2.0 SDKs ignore it) | `paywall.ts` | `definitions.json`, the definitions in `render-pages.json` |
| Event `sansora.event/1` | `sdk-events.ts` | `sessions.json` |
| Delivery config `sansora.config/1`, assignment, placement resolution | `sdk-config.ts` | `hash.json`, `resolution.json` |
| Audience rules | `campaigns.ts` (`ruleMatches`, `audienceMatches`) | `audience.json` |
| Render model `sansora.render/1`, prices | `sdk-render.ts` | `render.json`, `prices.json`, `price-format.json` |
| Pages and translated text (docs/PAYWALLS.md); store-specific legal text (§8) | `sdk-render.ts`; the store view: `forStore` in `sdks/conformance/generate.ts` | `render-pages.json` (cases with a `store` field are drawn for that store only) |
| Event emission per scripted session, durable delivery | `sdk-session.ts` | `sessions.json`, `delivery.json` |
| ISO 3166 alpha-2 → alpha-3 | — | `countries.json` |

Fixtures are generated by `node --import tsx sdks/conformance/generate.ts`
(never edit them by hand). Each SDK's test suite replays **every** fixture file
it is responsible for and must match exactly (`countries.json` is copied into
each SDK as source/resources).

`sdkVersion` is the package version, `0.2.1` on all four (they are versioned together).
The server accepts any `x.y.z` (optionally `-pre`), so apps on 0.1.0 keep delivering
events; it is stored with each event and shown per platform, and nothing depends on its
value. Platform values: `ios`, `android`, `flutter`, `react_native`.

## 1. Network

Base URL default `https://api.sansora.my` (overridable for tests and the local
desktop).

- `GET {base}/v1/sdk/config` with header `X-Sansora-Key: pk_…` and, when a
  cached copy exists, `If-None-Match: <etag>`. `200` → a `sansora.config/1` JSON
  document (+ `ETag`); `304` → keep the cache. Anything else, a parse failure or
  a `schema` other than `sansora.config/1` keeps the previous config.
- `POST {base}/v1/sdk/events`, `Content-Type: application/json`, body
  `{"key":"pk_…","events":[…]}` (1–100 events). Answer `{accepted, duplicates,
  rejected:[{index,eventId,reason}]}`.

Config source order: cached download → bundled fallback (a `sansora.config/1`
file the app ships, produced by `sansora paywalls pull`) → none. Refresh at
configure and on foreground when the cached copy is older than 15 minutes.

## 2. Public API (idiomatic per platform, same meaning)

- `configure(publicKey, options)`; options: `appUserId?`, `baseUrl?`,
  bundled config (file/asset/JSON), log level. Validates the key with
  `^pk_(test|live)_[a-z0-9]{24}$`.
- `identify(appUserId)`, `reset()` (new anonymous ID). Without `identify`, the
  SDK makes and persists `anon-<uuid v4>`. appUserId: 1–128 visible ASCII.
- `setAttributes(map)`: custom attributes, keys `^[a-z][a-z0-9_]{0,39}$`, values
  string/number/bool, at most 20. Used for audiences as `custom.<key>` and sent
  as `attributes` on `placement_fired`.
- `register(placement) → result`: fire a placement; if resolution gives a
  paywall, present it natively. Result: `purchased | restored | closed |
  holdout | no_campaign(reason) | no_config | ignored` (`ignored`: a paywall is
  already open; no events).
- `getPaywall(placement)`: resolution + definition without presenting (headless
  use / custom presentation). Emits no events and records no history.
- Optional **purchase controller** (app-owned purchases): `purchase(storeProductId)
  → purchased|trial|cancelled|pending|failed(reason)` and `restore() →
  restored|nothing|failed`. When set, the paywall's button and Restore call it
  instead of the store; prices still come from the store, every event is still
  emitted, and the native store no longer finishes/acknowledges transactions on
  its own. Built in React Native so far (iOS, Android and Flutter: not yet).
- `restorePurchases()`, `subscriptionStatus()` (`never|trial|active|lapsed`),
  `flush()`.
- `openPreview(code)` (test keys only): `GET {base}/v1/sdk/preview/{code}` with the key
  header. `200` → `{schema:"sansora.preview/1", definition}`; `404` →
  `no_campaign(preview_not_found)`; `403` → `no_campaign(preview_test_key_required)`;
  anything else → `no_campaign(preview_unavailable)`. The code is forgiving: spaces, dashes
  and case are ignored, I/L read as 1 and O as 0. It draws the definition with store prices
  and the label “Preview · purchases are off”, emits no events, records no history, and
  purchase and restore do nothing. Result `closed` when dismissed.

## 3. Device attributes for audiences (`campaigns.ts` names)

`storefront` (alpha-2, uppercase), `language` (lowercase primary language of the
preferred locale), `device` (`iphone|ipad|android_phone|android_tablet`),
`os_version`, `app_version`, `days_since_install` (whole days since the SDK first
ran, stored on first configure), `sessions` (cold start, or foreground after ≥30
minutes in background, starts a new session), `subscription` (from the store:
active in a free trial → `trial`, active → `active`, had one that ended →
`lapsed`, else `never`), `paywall_declined` (count of `paywall_closed` with
reason `closed`), `days_since_decline`, `custom.<key>`. `apple_ads_*` are not
collected automatically (AdServices needs a server call); a missing attribute
never matches.

## 4. Resolution and history

Exactly `resolvePlacement` in `sdk-config.ts`: campaigns on the placement by
priority (1 first, then id); first with a matching audience and an allowing
frequency cap decides; campaign holdout by
`bucket("holdout:<campaignId>:<appUserId>") < holdoutBps`; experiment arm by
`bucket("experiment:<experimentId>:<appUserId>")` over cumulative allocations
in config order. `bucket` = first 4 bytes of SHA-256(UTF-8 seed), big-endian
unsigned, mod 10000. Event `variant` = arm name when it is `A`/`B`, otherwise
the paywall version's editor variant.

History persisted on the device: `paywall_shown` times per campaign (keep the
latest 50 per campaign) and, in memory, the campaigns shown in the current
session. Only one paywall shows at a time; a `register` while one is open is
ignored (no events).

## 5. Events

Exactly as `runSession` in `sdk-session.ts` (all fields, order, values).
Every event: `schema`, `eventId` (UUID v4, lowercase, made once), `appUserId`,
`event`, `occurredAt` (ms), `platform`, `sdkVersion`, `osVersion` (≤20 chars),
`device` (model identifier ≤40 chars: iOS `utsname.machine`, or
`SIMULATOR_MODEL_IDENTIFIER` in the Simulator; Android `Build.MODEL`),
`storefront` (alpha-3, omitted when unknown; the last known storefront is
persisted and used until the store answers, so early events keep it), `store` (`app_store` on iOS,
`google_play` on Android). While a paywall is open, events also carry
`placement`, `paywallId`, `variant`. Purchase events carry the **store** product
ID. `paywall_closed` carries `durationMs` and `reason`
(`closed|purchased|restored`). `purchase_failed.reason`: `cancelled`, `pending`,
or a store error string. `restore_completed.reason`: `restored`,
`nothing_to_restore`, `failed`. When the store prices fail, the paywall still
shows (with “Price unavailable” and a disabled button) after
`prices_load_failed`: reason = the store error, `products_not_found` when
the store answers but any product in the definition with a store product ID is
missing from the answer, or `timeout` when the store sends no answer within 15 s.

**Prices on their way (0.2.1).** The paywall is drawn as soon as the placement resolves, before
the store answers (§8), and the events stay those of `runSession`'s `register` step: `paywall_shown`
waits for the store's answer (`prices_load_failed` first when it failed), but no longer than the
3-second wait or the person's first action (close, plan, restore). Then it is sent at once, and a
failure that comes later follows it. The display history records the moment the paywall was drawn,
and `paywall_closed.durationMs` counts from then. A store answer for a paywall that has closed is
dropped. Before 0.2.1 nothing was drawn until the store answered.

## 6. Delivery

Exactly `runDelivery` in `sdk-session.ts`: a persisted FIFO queue (survives app
restarts; at most 1000 events, oldest dropped), batches of ≤100 in order. 2xx
removes the batch; 400/413/422 drop it; everything else (incl. network errors)
keeps it and retries after `min(300 s, 2 s × 2^(failures−1))` plus 0–20% random
jitter (injectable; 0 in tests). Flush after enqueue (debounced ~1 s), on
background, on configure and when the retry timer fires. Never block the main
thread.

## 7. Store (purchases)

- **iOS, StoreKit 2:** `Product.products(for:)`; `displayPrice`, `price`
  (→ micros), currency from `priceFormatStyle.currencyCode`; free trial =
  `subscription.introductoryOffer` with `paymentMode == .freeTrial` **and**
  `await subscription.isEligibleForIntroOffer`, days = period value × (day 1,
  week 7, month 30, year 365). `purchase()` → verified transaction → `finish()`
  → `trial_started` when the transaction used the free-trial intro offer, else
  `purchase_completed`; `.userCancelled` → `cancelled`; `.pending` → `pending`;
  unverified → `unverified`. Listen to `Transaction.updates` from configure and
  finish them. Restore = `AppStore.sync()` then `Transaction.currentEntitlements`.
- **Android, Play Billing 8:** `enablePendingPurchases(one-time products)`,
  automatic service reconnection. `queryProductDetailsAsync` (subs and inapp).
  For subscriptions, pick the offer with a free phase
  (`priceAmountMicros == 0`; Play only returns offers the user is eligible
  for) else the base plan; trial days from the free phase's ISO 8601 period ×
  cycles; price from the recurring phase. On `PURCHASED`, **acknowledge**
  (unacknowledged purchases are refunded after 3 days) then emit. Restore =
  `queryPurchasesAsync` (subs + inapp), acknowledge any unacknowledged.
- **Flutter / React Native** call the native store classes through the bridge.

### Purchase confirmation

`POST {base}/v1/sdk/purchases/confirm`, `Content-Type: application/json`, exactly
`{"key","appUserId","store":"app_store","signedTransaction":"<StoreKit 2 jwsRepresentation>"}`
or `{"key","appUserId","store":"google_play","purchaseToken","productId":"<Play product ID>"}`
(the route rejects any other field). Answer `{status:"verified"|"reported",environment,productId,expiresAt}`.
It ties a purchase to the app user. `409 already_linked`: this purchase belongs to another user;
`409 not_configured`: store notifications aren't set up for the app. Sending the same purchase
again for the same user changes nothing. See `docs/STORE_REVENUE.md`.

All four SDKs confirm from native store code (`StoreKitStore`, `PlayBillingStore`); Flutter and
React Native tell native the current user (`setPurchaseUser` on configure, `identify` and `reset`).

- **What is confirmed:** every purchase the store code handles for the first time. iOS: a
  verified, unrevoked transaction from `purchase()` or `Transaction.updates` (renewals, Ask to
  Buy, other devices, unfinished ones), keyed by `originalID`. Android: every `PURCHASED`
  purchase from the purchase flow or `PurchasesUpdatedListener`, and one that restore finds
  unacknowledged; product ID = the purchase's first product. Restoring purchases that were
  already finished or acknowledged sends nothing. Unverified, pending and cancelled purchases
  send nothing; app-owned purchases (purchase controller) send nothing.
- **Never in the way:** the purchase is written to a local queue before `finish()` /
  acknowledge, and nothing waits for the network. The purchase result, events and finishing
  are the same whatever the route answers.
- **Queue:** persisted (`purchase-confirmations.json` beside the event queue), at most 100
  entries (oldest dropped), sent one at a time in order. Each entry keeps the user at the time
  of the purchase; one that arrives before the user is known waits for it. A waiting entry for
  the same transaction (iOS `originalID`) or token and user is replaced, not added. 2xx removes
  it; every other 4xx except 429 drops it (debug log with the status only); network errors,
  429, 5xx and anything else keep it and retry with §6's backoff. Flush after enqueue
  (debounced), on configure, on background, on `flush()` and when the retry timer fires.
- Purchase tokens and signed transactions are never logged.

## 9. Layout of `sdks/`

`ios/` (SwiftPM `SansoraKit` + podspec, example app), `android/` (Gradle library
`com.sansavision:sansora-android`, example app), `flutter/` (`sansora_flutter`
plugin + example), `react-native/` (`@sansavision/sansora-react-native` + example),
`conformance/`. No CI workflows (GitHub Actions are prohibited in this repo).
